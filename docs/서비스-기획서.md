## 1. 서비스 개요

### 1-1. 만들게 된 배경

소규모 요리교실은 대부분 강사 한 사람이 혼자 운영한다.
그런데 수업 하나를 여는 데 필요한 준비는 생각보다 많다.

- 오늘 오는 수강생이 몇 명이고, 나이대가 어떻게 되는지에 따라 진행 속도가 달라진다
- 90분과 120분은 같은 요리를 가르쳐도 구성이 완전히 다르다
- 재료를 몇 인분 준비할지, 도구가 몇 세트 필요한지 매번 다시 계산해야 한다
- 처음 오는 사람이 섞여 있으면 어느 지점에서 반드시 설명을 끼워야 한다

이 계산을 매 수업 전에 종이에 다시 적는다. 반복되는 일인데도 자동화되어 있지 않다.

**수업 설계소는 이 반복을 대신한다.**
수강생 조건 몇 가지를 입력하면 그날의 진행표, 준비물, 강사 멘트를 한 번에 만들어준다.

### 1-2. 서비스 목적

| 목적 | 설명 |
|---|---|
| 준비 시간 단축 | 수업 전 30~60분 걸리던 계획 수립을 3분으로 |
| 누락 방지 | 인원수 기준 재료·도구 수량을 자동 계산해 빠뜨리는 것을 막음 |
| 진행 안정화 | 시간 배분과 강사 멘트를 미리 확보해 수업 중 당황하지 않게 함 |

### 1-3. 목적이 아닌 것 (범위 밖)

의도적으로 넣지 않은 것을 함께 밝힌다.

| 안 하는 것 | 이유 |
|---|---|
| 레시피 자체를 알려주는 기능 | 강사는 이미 레시피를 안다. 필요한 건 "가르치는 방법"이다 |
| 수강생 예약·결제 관리 | 별도 도구가 이미 많고, 이 과제 범위를 넘어선다 |
| 회원 가입·로그인 | 로그인 없이 즉시 쓸 수 있는 편이 강사에게 유리하다 |

## 2. 타겟 사용자

### 2-1. 주 타겟

**소규모 요리교실을 혼자 운영하는 강사**

| 항목 | 내용 |
|---|---|
| 규모 | 1회 4~12명 |
| 운영 형태 | 강사 1인이 기획·준비·진행·정리를 모두 담당 |
| 수업 빈도 | 주 1~3회 |
| 겪는 문제 | 수업마다 구성이 달라 매번 처음부터 계획을 다시 세움 |
| 기술 수준 | 스마트폰·웹은 익숙하나 전문 도구는 부담스러움 |

### 2-2. 사용 상황 (이 서비스가 실제로 열리는 순간)

> 수업 전날 밤, 또는 수업 당일 아침.
> 재료를 사러 가기 전에 "오늘 뭐가 얼마나 필요하지"를 확인하려 할 때.
> **주방에 서 있거나 손에 짐을 든 상태인 경우가 많다.**

이 상황이 아래 두 가지 설계 결정의 근거가 된다.

| 설계 결정 | 근거 |
|---|---|
| 음성 입력 지원 | 손이 젖어 있거나 짐을 든 상태에서 타이핑이 어렵다 |
| PDF 다운로드 | 수업장에는 화면보다 종이가 편하다. 인쇄해서 들고 다닌다 |

### 2-3. 보조 타겟

- 문화센터·주민센터 단발성 요리 강좌 진행자
- 학교·기관에서 요리 체험 프로그램을 맡은 담당자

## 3. 페이지 / 섹션 구성

### 3-1. 구성 (총 5개 섹션)

| # | 섹션명 | 역할 | 주요 요소 |
|---|---|---|---|
| 1 | 메인 | 서비스가 무엇인지 3초 안에 전달 | 헤드라인, 한 줄 설명, "설계 시작" 버튼 |
| 2 | 수업 설계 | **핵심 기능.** 조건 입력 → AI 결과 출력 | 입력 폼, 로딩 표시, 결과 진행표, PDF 버튼 |
| 3 | 내 보관함 | 만든 설계를 다시 꺼내 봄 | 저장된 설계 카드 목록, 삭제 |
| 4 | 운영 가이드 | 사용법과 자주 묻는 질문 | 3단계 사용법, FAQ 4개 |
| 5 | 문의 | 의견·개선 요청 접수 | 이름·이메일·내용 폼 |

> 과제 요구사항은 "최소 3개 이상"이나, 서비스가 성립하려면 결과 보관과 사용 안내가 필요하다고 판단해 5개로 구성했다.

### 3-2. 페이지 구조 방식

**단일 페이지(index.html) + 앵커 이동** 방식을 채택한다.

| 선택지 | 채택 | 이유 |
|---|---|---|
| 여러 HTML 파일로 분리 | ✗ | 페이지 이동마다 새로 로딩되어 흐름이 끊긴다 |
| 단일 페이지 + 앵커 이동 | ✓ | 이동이 즉시 일어나고, 모바일에서 스크롤 경험이 자연스럽다 |

### 3-3. 네비게이션 방식

| 화면 크기 | 방식 |
|---|---|
| 데스크톱 (768px 초과) | 상단 고정 헤더에 메뉴 5개를 가로로 배치 |
| 모바일 (768px 이하) | 햄버거 버튼(☰) → 눌렀을 때 세로 메뉴 펼침 |

- 메뉴 클릭 시 해당 섹션으로 부드럽게 스크롤 이동
- 현재 보고 있는 섹션의 메뉴에 표시가 남음

## 5. AI 기능 설계

### 5-1. 입력

| 항목 | 형식 | 필수 | 예시 |
|---|---|---|---|
| 수강생 인원 | 숫자 (1~30) | ✅ | `8` |
| 연령대 | 선택 | ✅ | 성인 |
| 수업 시간 | 선택 (60/90/120/180분) | ✅ | 120분 |
| 요리 경험 | 선택 (처음/조금/익숙) | ✅ | 처음 |
| 만들 음식 | 텍스트 | ✅ | `잡채와 겉절이` |
| 특이사항 | 텍스트 (선택) | ❌ | `칼 사용을 최소화하고 싶어요` |

### 5-2. 처리 — AI를 두 번 나눠 호출한다

한 번의 호출로 전부 만들게 하면 결과가 뭉개진다.
특히 **시간 배분이 부정확해지고**, 총합이 수업 시간과 맞지 않는 경우가 자주 생긴다.

그래서 두 단계로 나눈다.

| 단계 | 시키는 일 | 받는 것 |
|---|---|---|
| **1차 호출** | 수업의 뼈대만 짜기 (단계 구분과 시간 배분) | 단계 목록 + 각 단계 소요 시간 |
| **2차 호출** | 1차 결과를 넣고 살 붙이기 | 각 단계의 강사 멘트, 준비물, 주의사항 |

**이렇게 하는 이유**: 한 번의 호출이 한 가지 일에만 집중하면 결과가 정확해진다.
1차는 "시간 계산"만, 2차는 "내용 작성"만 한다.

### 5-3. 출력

AI는 문장이 아니라 **데이터(JSON)** 로 응답한다. 화면은 그 데이터를 받아 자바스크립트가 직접 그린다.

```
{
  "title": "잡채와 겉절이 - 성인 초보 8인 120분 수업",
  "timetable": [
    { "time": "00:00", "duration": 10, "activity": "인사 및 오늘 메뉴 소개",
      "script": "오늘은 잡채와 겉절이를 만들겠습니다. 잡채는 재료를 따로 볶는 게 핵심이에요." }
  ],
  "materials": {
    "ingredients": [ { "name": "당면", "amount": "800g", "note": "1인 100g 기준" } ],
    "tools": [ { "name": "프라이팬", "count": 4, "note": "2인 1조" } ]
  },
  "cautions": [ "초보 수강생이라 칼질 단계에서 개별 확인이 필요합니다" ],
  "balance": "실습 시간이 전체의 70%로 초보자 대상 수업에 적절합니다"
}
```

**출력을 데이터로 받는 이유**
AI가 완성된 문장을 주면 화면에 그대로 붙일 수밖에 없다.
데이터로 받으면 표로도, 카드로도, PDF로도 그릴 수 있다. 화면 구성의 주도권이 이쪽에 남는다.

### 5-4. 사용자에게 제공하는 가치

| 입력 전 | 출력 후 |
|---|---|
| "8명이면 재료 얼마나 사야 하지?" | 인원 기준으로 계산된 재료 목록 |
| "120분을 어떻게 쪼개지?" | 분 단위 진행표 |
| "초보가 많은데 어디서 막힐까?" | 주의가 필요한 지점 표시 |
| 매번 종이에 다시 적음 | 저장해두고 다시 꺼내 쓰거나 인쇄 |

## 6. 실패 처리 기준

과제 요구사항은 "최소 1개 이상"이나, **세 가지 모두 구현한다.**
AI 기능은 실패하는 방식이 서로 다르고, 각각 사용자가 해야 할 행동도 다르기 때문이다.

| # | 상황 | 판단 기준 | 사용자에게 보이는 것 | 사용자가 할 일 |
|---|---|---|---|---|
| 1 | **빈 입력** | 필수 항목이 비었거나 공백만 있음 | 해당 입력칸이 빨갛게 표시되고<br>"만들 음식을 입력해 주세요" | 값을 채운다 |
| 2 | **API 오류** | 응답 상태가 4xx 또는 5xx | "설계에 실패했어요.<br>잠시 후 다시 시도해 주세요."<br>+ 다시 시도 버튼 | 버튼을 다시 누른다 |
| 3 | **지연 / 타임아웃** | 20초 경과 → 안내<br>30초 경과 → 중단 | 20초: "시간이 조금 걸리고 있어요. 기다려 주세요."<br>30초: "응답이 너무 늦어 중단했습니다." | 기다리거나 다시 시도 |

### 6-1. 빈 입력은 서버까지 보내지 않는다

빈 입력은 **화면(JS)에서 먼저 걸러낸다.** 서버로 보내지 않는다.

**이유가 두 가지 있다.**

| 이유 | 설명 |
|---|---|
| 속도 | 서버를 거치면 1~2초 뒤에야 "비었어요"를 알게 된다. 즉시 알려주는 편이 낫다 |
| 비용 | AI 호출은 건당 요금이 발생한다. 빈 요청에까지 돈을 쓸 이유가 없다 |

### 6-2. 오류 메시지에 기술 용어를 쓰지 않는다

`500 Internal Server Error` 를 그대로 보여주지 않는다.
사용자는 그 숫자로 할 수 있는 일이 없다. **다음에 뭘 하면 되는지**만 알려준다.

기술적인 원인은 개발자 도구 콘솔에만 남긴다.

## 7. 기술 구성

| 영역 | 사용 기술 | 비고 |
|---|---|---|
| 프론트엔드 | HTML5, CSS3, 순수 JavaScript | 프레임워크 미사용 (과제 조건) |
| 반응형 | CSS 미디어 쿼리, Flexbox, Grid | 768px / 1024px 기준 |
| 백엔드 | Vercel Serverless Functions (Python) | `api/` 폴더 |
| AI | Claude API | 환경 변수로 키 관리 |
| 배포 | Vercel (GitHub 연동 자동 배포) | |
| 버전 관리 | Git, GitHub | |

### 7-1. 데이터가 흐르는 순서

```
사용자가 폼 입력
      ↓
JS가 빈 값 검사 (빈 값이면 여기서 중단)
      ↓
fetch('/api/design') 로 요청 전송
      ↓
Vercel의 Python 함수가 깨어남
      ↓
환경 변수에서 API 키를 꺼냄
      ↓
AI 1차 호출 (뼈대) → AI 2차 호출 (상세)
      ↓
JSON으로 응답 반환
      ↓
JS가 받아서 표를 그림
```

### 7-2. API 키를 환경 변수로 관리하는 이유

| | 결과 |
|---|---|
| 코드에 키를 적으면 | GitHub가 Public이므로 **누구나 볼 수 있다**. 남이 쓴 요금이 나에게 청구된다 |
| 환경 변수에 두면 | 코드에는 "키를 꺼내 쓴다"는 문장만 남고, 실제 값은 Vercel 설정에만 존재한다 |

`.gitignore` 첫 줄에 `.env` 를 넣어둔 것이 이 대비다.
저장소를 만들기 전에 미리 넣었다 — 한 번 올라간 기록은 파일을 지워도 이력에 남기 때문이다.

## 8. 개발 범위와 순서

기능을 두 층으로 나눈다. **아래층이 완전히 동작한 뒤에만 위층에 손을 댄다.**

### 8-1. 필수층 (이것만으로 과제 요구사항 충족)

| # | 항목 | 대응하는 요구사항 |
|---|---|---|
| 1 | 5개 섹션 + 네비게이션 | 4-3 |
| 2 | 반응형 레이아웃 | 4-4 |
| 3 | 입력 폼 + 결과 표시 | 4-5 |
| 4 | Python 서버리스 + AI 연동 | 4-6 |
| 5 | 실패 처리 3종 | 4-5 |
| 6 | Vercel 배포 | 4-7 |

### 8-2. 보너스층 (배포 성공 후에만 착수)

| # | 항목 | 대응하는 보너스 과제 |
|---|---|---|
| 7 | AI 2단계 호출 | — (품질 향상) |
| 8 | PDF 다운로드 | 보너스 1 (운영 흐름 확장) |
| 9 | 음성 입력 | 보너스 2 (UX 고도화) |
| 10 | 보관함 저장 | 보너스 1 (데이터 저장) |
| 11 | 호출 제한·캐싱 | 제약사항 (과금·쿼터 대응) |

**이 순서를 정한 이유**
보너스 기능을 먼저 만들다 배포에 실패하면 과제 자체가 성립하지 않는다.
필수층이 배포되어 동작하는 시점에서 이미 제출 가능한 상태가 되고,
그 위에 얹는 것은 실패해도 되돌리면 그만이다.
